# Monitoring-rule revision API

The API exposes the per-instrument monitoring-rule timeline under `/api/watched-instruments/{instrumentId}/monitoring-rule`. The timeline is continuous: from its coverage origin onward every instant resolves to exactly one committed revision. Drafts are working proposals that live outside the committed timeline until they are applied or scheduled.

This document covers request shapes, the concurrency protocol and the problem codes each endpoint can return. See [Architecture](architecture.md) for the domain rules the API enforces and [Current configuration persistence](current-configuration-persistence.md) for the storage model.

## Concepts

- **Committed revision** — a definition effective over a half-open `[effectiveFrom, effectiveTo)` instant range; `effectiveTo` null means open-ended.
- **Draft** — a proposed definition with optional `proposedEffectiveFrom`/`proposedEffectiveTo` dates. Drafts never affect applicability until committed.
- **Coverage origin** — the earliest covered instant, fixed at rule creation. It can never be rewritten, rescheduled or removed.
- **Continuation** — a system-created revision carrying the remainder of a covered period when a bounded insertion splits it in three. Its identifier is generated by the API layer.
- **Concurrency token** — the SQL `rowversion` of the rule row, surfaced as a base64 string in `concurrencyToken` fields and the `ETag` header.

## Optimistic concurrency

Every mutating endpoint requires the current concurrency token in an `If-Match` header.

- Read the token from `concurrencyToken` in any timeline, revision or drafts response, or from the response `ETag` header (`"<base64>"`).
- Send it back as `If-Match: "<base64>"`. Quoted, unquoted and weak (`W/`) tags are accepted.
- A missing header returns `428 Precondition Required` (`monitoring_rule.concurrency_token_required`). A malformed value returns `400` (`monitoring_rule.concurrency_token_invalid`). A stale value returns `412 Precondition Failed` (`monitoring_rule.concurrent_change`) — reload the timeline and retry.
- Every successful write returns the fresh token in `ETag` and `concurrencyToken`; the next write must use it.

## Endpoints

| Method and path | Purpose | Success |
| --- | --- | --- |
| `GET .../monitoring-rule` | Full committed timeline plus `coverageOrigin` | `200` timeline response |
| `GET .../monitoring-rule/drafts` | All drafts | `200` drafts response |
| `GET .../monitoring-rule/revisions/{revisionId}` | One revision or draft by id | `200` revision response |
| `GET .../monitoring-rule/revisions/applicable?at={instant}` | Revision effective at `at`; defaults to server now when omitted | `200` revision response |
| `POST .../monitoring-rule/drafts` | Create a draft | `200` timeline response |
| `PUT .../monitoring-rule/drafts/{draftId}` | Replace a draft's definition, reason and proposal | `200` timeline response |
| `DELETE .../monitoring-rule/drafts/{draftId}` | Discard a draft | `200` timeline response |
| `POST .../monitoring-rule/drafts/{draftId}/apply` | Commit a draft open-ended from server now | `200` timeline response |
| `POST .../monitoring-rule/drafts/{draftId}/schedule` | Commit a draft over `[effectiveFrom, effectiveTo)` | `200` timeline response |
| `PUT .../monitoring-rule/revisions/{revisionId}` | Edit a future revision's definition and/or move its start | `200` timeline response |
| `DELETE .../monitoring-rule/revisions/{revisionId}` | Remove a future revision; predecessor reopens | `200` timeline response |

All paths are relative to `/api/watched-instruments/{instrumentId}`.

### Request bodies

`POST /drafts` and `PUT /drafts/{draftId}` accept:

```json
{
  "changeReason": "raise support",
  "proposedPeriod": { "effectiveFrom": "2026-10-06T10:00:00Z", "effectiveTo": null },
  "definition": {
    "priceScale": 4,
    "supportZones": [
      {
        "id": "support-a",
        "lower": 105.0,
        "level": 110.0,
        "upper": 115.0,
        "conditions": [
          { "type": "buy-zone", "actionId": "publish-signal" }
        ]
      }
    ],
    "resistanceZones": []
  }
}
```

`proposedPeriod` may be null or carry either bound; it records intent and is never enforced automatically. `definition` is required and is validated by the same chart-analysis rules used at registration.

`POST /drafts/{draftId}/schedule` accepts `{ "effectiveFrom": "2026-10-06T10:00:00Z", "effectiveTo": null }`. `effectiveFrom` is required and must be at or after server now; `effectiveTo` null commits open-ended and replaces all covered future revisions.

`PUT /revisions/{revisionId}` accepts `{ "changeReason": "…", "definition": {…}, "effectiveFrom": "…" }`; both fields are optional — `definition` replaces the scheduled definition, `effectiveFrom` reschedules the start boundary.

`POST /drafts/{draftId}/apply`, `DELETE /drafts/{draftId}` and `DELETE /revisions/{revisionId}` take no body.

### Response shapes

Timeline response (`monitoring-rule` and every successful write):

```json
{
  "monitoringRuleId": "…",
  "watchedInstrumentId": "…",
  "concurrencyToken": "AAAAAAAAB9E=",
  "coverageOrigin": "2026-01-02T09:30:00Z",
  "revisions": [ /* committed revisions in effectiveFrom order */ ]
}
```

Drafts response mirrors it with a `drafts` array. A revision object carries `id`, `kind` (`draft` or `committed`), `revisionNumber` (null for drafts), `createdAt`, `createdBy`, `changeReason`, `effectiveFrom`/`effectiveTo`, `proposedEffectiveFrom`/`proposedEffectiveTo` and `definition`.

## Problem codes

Failures are RFC 7807 Problem Details with a stable `code` extension.

| Status | Code | Cause |
| --- | --- | --- |
| 400 | `monitoring_rule.request_required` | Missing body on an endpoint that needs one |
| 400 | `monitoring_rule.definition_required` | Draft request without a definition |
| 400 | `monitoring_rule.instant_invalid` | Unparseable `at` or missing `effectiveFrom` |
| 400 | `monitoring_rule.instant_not_persistable` | Instant finer than 100 ns or outside the persisted range |
| 400 | `monitoring_rule.concurrency_token_invalid` | Malformed `If-Match` value |
| 400 | `chart_analysis.*` | Definition validation failures (zone boundaries, condition types, duplicates) |
| 400 | `revision.backdated` | Commit start earlier than server now |
| 400 | `revision.invalid_period` | Zero-length or inverted requested period |
| 400 | `revision.uncovered_start` | Insert start before the coverage origin |
| 404 | `monitoring_rule.not_found` | No rule for the instrument |
| 404 | `monitoring_rule.no_applicable_revision` | Nothing committed at `at` (before the origin) |
| 404 | `revision.not_found` | Unknown draft or revision id |
| 409 | `revision.duplicate_id` | Identifier collision on commit |
| 409 | `revision.period_begun` | Edit or commit touching a period that already began |
| 409 | `revision.coverage_origin_protected` | Reschedule/remove targeting the origin revision |
| 412 | `monitoring_rule.concurrent_change` | Stale `If-Match` token |
| 428 | `monitoring_rule.concurrency_token_required` | Missing `If-Match` on a write |

`createdBy` on committed revisions is resolved from the caller identity (`preferred_username`, `oid` or `sub` claim). Locally, without Easy Auth, it records `unverified-local-caller`.
